# Porting Notes: Processing (Java) to p5.js (JavaScript)

This document describes every significant decision made in porting the Outer Wilds Text Adventure from Processing to p5.js. It is intended as a reference for anyone comparing the port against the original source, maintaining the port, or doing a similar Processing-to-p5.js port.

The original source files are `.pde` files (Processing/Java). Each ported `.js` file has a header comment identifying its source. Files new to the port (no `.pde` counterpart) are noted below.

## New Files

These `.js` files have no direct `.pde` counterpart:

**`bitmapFont.js`** — Custom bitmap font renderer. Processing natively renders `.vlw` bitmap fonts via `textFont()`/`text()`. p5.js has no `.vlw` support, so this file provides a renderer that takes pre-parsed glyph data (generated by `tools/convert-assets.js` from the original `.vlw` files) and overrides p5.js's `text()`, `textWidth()`, `textSize()`, `textAlign()`, and `fill()` to route through the bitmap renderer. See [Bitmap Font System](#bitmap-font-system) for details.

**`enums.js`** — Replaces Java `enum` types (`SectorName`, `Frequency`, `Curiosity`) used throughout the original `.pde` files. JavaScript has no native enum construct, so these are implemented as frozen objects with string values (e.g., `SectorName.COMET === 'COMET'`). The original Java enums support `.ordinal()` and `.values()` which are not directly available — see `telescope.js`'s `FREQUENCY_VALUES` array for how ordinal cycling is handled.

**`signal.js`** — The `Signal` class, extracted from `Telescope.pde` (lines 167-185). Separated into its own file because it's loaded in Phase 1 (Foundation) while the rest of the telescope code loads in Phase 3. The frequency parsing is slightly more lenient than the original: it calls `.toUpperCase()` before lookup, so it accepts `"quantum"` as well as `"QUANTUM"`. The original only accepts exact uppercase matches.

**`actor.js`** — `Actor`, `Player`, `Ship`, and `Probe` classes, extracted from `Entity.pde` (lines 99-267). In the original, all five classes (`Entity`, `Actor`, `Player`, `Ship`, `Probe`) are in one file. The port splits them for organizational clarity but they must load in order (entity.js before actor.js) due to the inheritance chain.

**`tools/convert-assets.js`** — Node.js script that converts sector `.json` files and `.vlw` bitmap font files into `.js` data files. See [Asset Loading](#asset-loading).

## Constructor Overloading

Java allows multiple constructors per class. JavaScript does not. Where the original has overloaded constructors, the port merges them into a single constructor that uses `typeof` or `instanceof` to distinguish which variant was called.

Example from `Node.pde`:
```java
// Two separate constructors in the original
Node(float x, float y) { ... }
Node(String id, JSONObject nodeObj) { ... }
```

Becomes in `node.js`:
```javascript
// Single constructor with type checking
constructor(idOrX, jsonObjOrY) {
  if (typeof idOrX === 'number') {
    // Node(x, y) path
  } else {
    // Node(id, jsonObj) path
  }
}
```

This pattern is used in:

| Class/Method | Original Overloads | JS Discrimination |
|---|---|---|
| `Vector2` constructor | `()`, `(float, float)`, `(Vector2)` | `instanceof Vector2` |
| `Entity` constructor | `()`, `(float, float)`, `(Vector2)` | `instanceof Vector2` |
| `Node` constructor | `(float, float)`, `(String, JSONObject)` | `typeof === 'number'` |
| `Button` constructor | `(String)`, `(String, float, float, float, float)` | default params via `\|\|` |
| `TravelAction` constructor | 4-arg and 5-arg variants | `arguments.length` / `undefined` check |
| `SignalSource` constructor | `(Node)`, `(Vector2, Sector)` | `instanceof Node` |
| `GlobalMessenger.sendMessage` | `(String)`, `(Message)` | `typeof === 'string'` |
| `GameManager.loadSector` | `(SectorName)`, `(Sector)` | `typeof === 'string'` |
| `Sector.addActor` | `(Actor)`, `(Actor, String)`, `(Actor, Node)` | `typeof` / `instanceof` |
| `Sector.getNode` | `(int)`, `(String)` | `typeof === 'number'` |
| `StatusFeed.publish` | `(String)`, `(String, boolean)` | default param via `\|\|` |
| `SectorButton.drawName` | `()`, `(String, float)` | `=== undefined` check |

The same pattern applies to method overloading (not just constructors), since JavaScript functions also cannot be overloaded.

## Java Interface Removal

The original defines five Java interfaces. JavaScript has no interface construct, so these are dropped entirely. The classes that implemented them still define the same methods — they just aren't enforced by the type system. This is standard duck typing: if an object has an `onReceiveGlobalMessage` method, it can be used as a global observer regardless of whether it formally declares that it implements the interface.

| Interface | Defined In | Methods | Implemented By |
|---|---|---|---|
| `GlobalObserver` | GlobalMessenger.pde | `onReceiveGlobalMessage(Message)` | GameManager, TimeLoop, SolarSystem, Sector, PlayerData |
| `ButtonObserver` | Button.pde | `onButtonUp(Button)`, `onButtonEnterHover(Button)`, `onButtonExitHover(Button)` | Screen (and all subclasses), SectorEditor |
| `NodeButtonObserver` | Node.pde | `onNodeSelected(Node)`, `onButtonEnterHover(Button)`, `onButtonExitHover(Button)` | SectorScreen, SectorEditor |
| `NodeObserver` | Node.pde | `onNodeVisited(Node)`, `onArrival(Node)`, `onQuantumEntanglement()` | Sector |
| `NodeActionObserver` | NodeAction.pde | `onTravelToNode(Node)`, `onExploreNode(Node)`, `onProbeNode(Node)` | SectorScreen |

The `abstract` keyword on classes (`Screen`, `SectorButton`, `NodeAction`) is also dropped. Abstract methods become empty stubs (e.g., `update() {}` on `Screen`).

## Lazy Color Initialization

Processing's `color()` function works at any time, including during field initialization. In p5.js, `color()` is not available until after `setup()` runs — calling it earlier throws an error because the color mode hasn't been configured yet.

Three classes originally initialized colors at field-declaration time:

- **Button** (`_buttonColor`): Changed from `color _buttonColor = color(0, 0, 100);` to a `_getButtonColor()` lazy getter that creates the color on first access.
- **StatusLine** (`_lineColor`): Changed from computing the color in the constructor to a `_getLineColor()` lazy getter. The `important` flag is stored so the color can be computed later.
- **ClueButton** (`_symbolColor`): Same pattern — deferred to first use.

In all cases, the lazy getter is called during `draw()`, which is always after `setup()`, so `color()` is available.

## Defensive Vector2 Copies

Java passes object references, but the original Processing code often treats `Vector2` values as if they were value types — setting `.x` and `.y` individually rather than assigning the reference. In JavaScript, assigning an object reference means both variables point to the same object, so mutations through one affect the other.

In a few places, the port explicitly copies Vector2 values to prevent unintended mutation:

- **`nodeAction.js` (ProbeAction.execute)**: `probe.setScreenPosition(new Vector2(this._player.screenPosition))` — the original passes the player's screenPosition directly. Without the copy, the probe and player would share the same screenPosition object, and moving one would move the other.

- **`telescope.js` (SignalSource constructor)**: `this.setScreenPosition(new Vector2(nodeOrPosition.screenPosition))` — same issue. Without the copy, the signal source's position would be a reference to the node's position.

- **`solarSystemScreen.js` (SolarSystemMapScreen.setActorPosition)**: Wraps positions in `new Vector2()` when setting actor positions from sector button positions.

In the original Java, `Entity.setPosition()` assigns to `position.x` and `position.y` individually (not by reference), so the original code doesn't have this problem. The copies in the port are a correctness fix, not a behavioral change.

## Processing JSON API to Bracket Notation

The original uses Processing's typed JSON API throughout:

| Processing | JavaScript Port |
|---|---|
| `obj.getString("key")` | `obj['key']` |
| `obj.getString("key", default)` | `obj['key'] ?? default` or `obj['key'] \|\| default` |
| `obj.getInt("key")` | `obj['key']` |
| `obj.getInt("key", default)` | `obj['key'] ?? default` |
| `obj.getBoolean("key", default)` | `obj['key'] ?? default` or `obj['key'] === true` |
| `obj.getJSONObject("key")` | `obj['key']` |
| `obj.getJSONArray("key")` | `obj['key']` |
| `obj.hasKey("key")` | `obj['key'] !== undefined` |

This works because p5.js's `loadJSON()` returns native JavaScript objects where bracket notation provides direct access to values with their correct types (numbers, strings, booleans, objects, arrays).

**Note on `||` vs `??`:** Some default-value patterns use `||` which treats `0`, `""`, and `false` as missing. The original's `getInt("key", default)` only falls back when the key is absent. We verified that the actual game JSON data does not contain `0`, `""`, or `false` for any of these fields, so the `||` pattern produces correct results in practice.

## Asset Loading

The original Processing game loads files at runtime:
- Sector JSON via `loadJSONObject("sectors/comet.json")` — relative to the sketch's `data/` directory
- Bitmap fonts via `loadFont("fonts/Consolas-14.vlw")`

In a browser, `fetch()` and `XMLHttpRequest` are blocked by CORS when loading from `file://` URLs (each local file is treated as a different origin). This means opening `index.html` directly from the filesystem would fail.

To avoid requiring a local server, the port pre-converts all data files into JavaScript using `tools/convert-assets.js`:

**Sector data:** Each `.json` file is wrapped as a JS variable assignment:
```javascript
// data/sectors/comet.js (generated)
sectorJSONData['comet'] = { "Sector Arrival": "...", "Nodes": {...}, "Connections": [...] };
```

**Font data:** The binary `.vlw` files are parsed once at build time. The script extracts the header (fontSize, ascent, descent), glyph metrics (value, width, height, setWidth, topExtent, leftExtent), and pixel alpha values for each glyph, outputting them as a JSON-in-JS structure:
```javascript
// data/fonts/Consolas-14.js (generated)
fontData[14] = { fontSize: 14, ascent: 11, descent: 3, glyphs: [...] };
```

At runtime, the glyph alpha arrays are converted into p5 `image` objects by `BitmapFont`'s constructor (white RGB + alpha from the data).

The `<script>` tags in `index.html` load these `.js` files before any game code runs, so `sectorJSONData` and `fontData` are fully populated by the time `setup()` is called.

The original `.json` and `.vlw` files are kept as the source of truth. To regenerate after editing:
```
node tools/convert-assets.js
```

**Audio** is loaded via `new Audio('data/audio/ow_kazoo_theme.mp3')`, which uses an `<audio>` element. Audio elements are exempt from CORS restrictions on `file://`, so no conversion is needed.

## push()/pop() vs pushMatrix()/popMatrix()

Processing provides two separate save/restore mechanisms:
- `pushMatrix()` / `popMatrix()` — saves/restores only the **transform** (translate, rotate, scale)
- `pushStyle()` / `popStyle()` — saves/restores only **style** (fill, stroke, textSize, etc.)

p5.js merged these into a single pair:
- `push()` / `pop()` — saves/restores **both** transform and style

p5.js deliberately deprecated `pushMatrix()`/`popMatrix()` — they exist only as error-throwing stubs that tell you to use `push()`/`pop()` instead.

The original code uses `pushMatrix()`/`popMatrix()` exclusively. In theory, replacing them with p5.js `push()`/`pop()` could cause behavioral differences: style changes made inside a push/pop block would be reverted on `pop()`, whereas in the original they persist.

In practice, we analyzed every call site and found no case where this difference matters — each drawing method sets its own fill/stroke/textSize before drawing, so any style that "leaks" from a `pushMatrix` block is overwritten before it's used.

The port uses p5.js's `push()`/`pop()` directly rather than attempting to override p5's error-throwing `pushMatrix`/`popMatrix` stubs. This is simpler, works with the framework instead of against it, and produces no observable rendering differences.

**Affected files** (all use `push()`/`pop()`): actor.js, node.js, sector.js, sectorButtons.js, telescope.js, exploreScreen.js, eventScreens.js, supernovaScreen.js, bitmapFont.js.

## Bitmap Font System

Processing's `.vlw` format is a binary bitmap font format:
- **Header** (24 bytes): glyphCount, version, fontSize, smooth flag, ascent, descent (all int32 big-endian)
- **Glyph headers** (28 bytes each): Unicode value, height, width, setWidth (advance width), topExtent, leftExtent, padding
- **Pixel data**: One byte per pixel per glyph (alpha channel only), stored sequentially after all glyph headers

The port's `tools/convert-assets.js` parses this binary format at build time and outputs the data as JavaScript objects. At runtime, `BitmapFont`'s constructor converts each glyph's alpha array into a p5 `image` (white RGB + the parsed alpha values), enabling tinting to apply fill color.

**Text rendering** works by drawing each character as an individual `image()` call, positioned using the glyph's `leftExtent` and `topExtent` offsets relative to the baseline. The advance width uses `setWidth` from the font data.

**Scaling**: `scale = renderSize / font.fontSize`. When `textSize(100)` is called with a 14px font, glyphs are scaled up ~7x, producing the same pixelated look as the original Processing rendering.

**Overrides**: `setupBitmapTextOverrides()` in `bitmapFont.js` replaces p5's global `text()`, `textWidth()`, `textSize()`, `textAlign()`, and `fill()` functions. When `BitmapText.enabled` is true and a font is active, calls are routed to the bitmap renderer. Otherwise they fall through to p5's originals.

**Fill color tracking**: `BitmapText.fillColor` is updated whenever the overridden `fill()` is called. For alignment and size, the system reads directly from `window._renderer._textAlign`, `_textBaseline`, and `_textSize` to stay in sync with p5's internal state (important after `push()`/`pop()` which restore p5's internals without calling the overridden functions).

**CSS fallback**: `textFont('Consolas, "Courier New", monospace')` is set in `setup()` as a fallback. It is not used for actual rendering — the bitmap system intercepts all `text()` calls. It exists so that if the bitmap system were disabled, text would still render in a monospace font.

## Audio

The original uses the **Minim** library (Java) for audio playback:
```java
static Minim minim;
static AudioPlayer kazooTheme;
```

The port uses the **HTML5 Audio API**:
```javascript
SoundLibrary.kazooTheme = new Audio('data/audio/ow_kazoo_theme.mp3');
```

Key differences:

- **Architecture**: The original uses a constructor-based `AudioManager` class with static methods. The port uses singleton objects (`SoundLibrary` and `AudioManager`) with an explicit `init()` method that must be called during `setup()`.
- **Autoplay policy**: Browsers block audio playback until the user interacts with the page. The port wraps `.play()` in a `.catch()` to suppress `NotAllowedError` from autoplay restrictions. The original has no such concern.
- **Play behavior**: The port adds `currentTime = 0` before each `play()` call, which always restarts from the beginning. The original's Minim `play()` resumes from the current position after a `pause()`. In practice this doesn't matter because the game only has one track and always starts it fresh.

## Mouse and Keyboard Input

- **`mousePressed` boolean** → `mouseIsPressed`: Processing exposes `mousePressed` as a boolean field indicating whether any mouse button is currently held. p5.js uses `mouseIsPressed` for the same purpose. The `mousePressed` name is reserved in p5.js for the event handler function. The `Button` class's `mousePressed()` method is renamed to `isMouseDown()` to avoid collision.

- **`mouseButton` values**: Processing uses integer constants (`LEFT = 37`, `RIGHT = 39`). p5.js uses string constants (`LEFT = 'left'`, `RIGHT = 'right'`). Since comparisons are always against the same constants (never hardcoded integers), this works transparently.

- **`exit()`**: Processing's `exit()` terminates the application. Browsers cannot close their own tab from JavaScript. The Quit button (TitleScreen) and Exit button (EndScreen) log to the console and do nothing visible.

- **Context menu**: The port prevents the browser's right-click context menu on the canvas (`contextmenu` event listener) so right-click can be used for game actions (probing nodes). Processing handles right-click natively.

## Collections and Data Structures

| Processing/Java | JavaScript Port |
|---|---|
| `ArrayList<T>` | `Array` (`[]`) |
| `HashMap<K, V>` | `Map` (for Node `_connections`) or plain objects |
| `FloatList` | `Array` (SupernovaScreen `_ringSizes`) |
| `ArrayList.clear()` | `array = []` (new array) or `array.length = 0` |
| `ArrayList.remove(obj)` | `array.splice(array.indexOf(obj), 1)` |
| `HashMap.get(key)` | `map.get(key)` |
| `HashMap.containsKey(key)` | `map.has(key)` |

The port uses `= []` (new array assignment) rather than clearing in place. This is safe because no code retains references to the old array.

## Type System Differences

- **`==` vs `===`**: Java's `==` on objects is reference equality. JavaScript's `===` is the equivalent. The port uses `===` throughout, which is stricter than JS `==` (no type coercion). This is correct for all comparisons in this codebase.

- **Integer division**: Java's `int / int` truncates toward zero. JavaScript's `/` always produces a float. The original code explicitly casts to `(float)` in the few places where float division is needed (e.g., `TimeLoop.getLoopPercent()`), and the game data doesn't rely on integer truncation behavior, so this is not an issue.

- **`final` keyword**: Java's `final` prevents reassignment. JavaScript's `const` only applies to the variable binding, not the object's contents. Fields like `Actor.SPEED` that were `final float SPEED = 10` in Java become `this.SPEED = 10` (mutable) in the port. Nothing in the codebase mutates these values.

- **`abstract` classes**: JavaScript has no `abstract` keyword. Abstract classes become regular classes with empty method stubs. Abstract methods like `Screen.update()` and `Screen.render()` become `update() {}` and `render() {}`.

## Rendering Differences

- **`pushMatrix()`/`popMatrix()`**: See [Transform Matrix Helpers](#transform-matrix-helpers).

- **`arc()` default mode**: Both Processing and p5.js (v1.9.4) draw arc fill as PIE and stroke as OPEN when no mode is specified. No adaptation needed — confirmed by reading the [p5.js source](https://github.com/processing/p5.js/blob/v1.9.4/src/core/p5.Renderer2D.js).

- **`noSmooth()`**: Processing disables anti-aliasing globally for all shapes, lines, and images. p5.js's `noSmooth()` only sets `imageSmoothingEnabled = false` on the canvas context, affecting image scaling but not shape/line anti-aliasing. This is a Canvas 2D API limitation — there is no way to disable shape AA. Lines and ellipses may appear slightly smoother in the port.

- **Font rendering**: Processing renders `.vlw` bitmap fonts natively. The port uses a custom bitmap renderer. See [Bitmap Font System](#bitmap-font-system).

- **Variable renaming in `nodeConnection.js`**: Variables `right` and `left` (used for arrow-drawing vectors) are renamed to `right2` and `left2` to avoid shadowing p5.js's built-in `RIGHT` and `LEFT` constants.

## Bugfixes

One bug in the original is fixed in the port:

**Actor removal during forward iteration** (`sector.js`): The original iterates actors forward (`for (int i = 0; i < _actors.size(); i++)`) while removing dead actors mid-loop. In Java's `ArrayList`, removing an element at index `i` shifts subsequent elements left, so the element at `i+1` moves to `i`, but the loop increments `i`, skipping it. The port iterates in reverse (`for (let i = this._actors.length - 1; i >= 0; i--)`), which is the standard safe pattern. In practice, the bug is unlikely to trigger because only the Probe actor returns `isDead() == true` and there's unlikely to be two adjacent dead probes.

## Platform Limitations

These are inherent differences between Processing (desktop Java app) and p5.js (browser) that cannot be fully bridged:

- **`noSmooth()` does not disable shape anti-aliasing** — Canvas 2D API limitation
- **`exit()` cannot close the browser tab** — browser security restriction
- **Audio may not autoplay** — browser autoplay policy requires user interaction first
- **No filesystem write access** — the sector editor's save function (`Sector.saveSectorJSON`) logs JSON to the console instead of writing to disk
